# Background jobs: inventory and monitoring plan

**Status: nothing in this repository schedules, runs or monitors any job.** Each job below is an HTTP endpoint that works when somebody calls it with the secret. Until the owner decides who schedules them (open decision, see "Owner decision needed"), none of them runs on its own. Do not read an endpoint's existence as "this runs".

All three job endpoints are `POST` only, answer `401` unless `Authorization: Bearer $JOBS_SECRET` matches (constant-time comparison, secret of 16+ characters), call the database through the service role, are safe to repeat, and record each run in `public.job_runs` (append-only) so the administrator page `/admin/jobs` and `admin_job_health()` can show last run, last success and failures in the last 24 hours. A job that was never called shows as **Never run**; that is a fact, not an error.

## Health endpoint

`GET /api/health` returns `{"ok":true}` (200) when the application can reach the database, `{"ok":false}` (503) when it cannot, and 429 when one address asks more than 60 times a minute. It reveals no version, configuration or counts. **Nothing calls it**: pointing an uptime monitor at it is a deployment step.

## Authentication of jobs

- One shared secret, `JOBS_SECRET` (server only; never `NEXT_PUBLIC_`; 16+ characters or the endpoints refuse everything). Rotating it means changing the value where the scheduler stores it and in the server environment together. There is no per-job secret.
- Callers need no other identity. The endpoints use the service-role database client; the functions they call are executable by `service_role` only (pinned by `schema-hygiene.test.ts` and `admin.test.ts`).

## Expected cadence (proposal, for the owner to confirm)

| Job                     | Suggested cadence | Why                                                                  |
| ----------------------- | ----------------- | -------------------------------------------------------------------- |
| Order expiry            | every 5 minutes   | The hold time is 30 minutes by default; late expiry strands stock.   |
| Notification processing | every minute      | Only matters once a real sink exists; the local sink is a rehearsal. |
| Location purge          | hourly            | Retention is configured in hours.                                    |

These cadences are suggestions, not decisions.

## Failure alerting

Not implemented. `/admin/jobs` and the overview counters ("Notifications that failed for good", "stuck in processing") show problems when an administrator looks. Nothing pages anyone. An alerting channel (and who is on call) is an owner/operations decision.

## Owner decision needed

Who schedules these jobs, on what infrastructure, and who is told when one fails. No paid scheduler or production schedule has been introduced. A free option exists later (for example a scheduler in the hosting platform or GitHub Actions calling the endpoints); choosing it is out of scope for this batch and needs approval.
