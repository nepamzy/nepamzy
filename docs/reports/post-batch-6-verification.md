## 3. Settings security (verified)

Read `supabase/migrations/20261016000001_settings_allowlist_reason.sql` and `tests/db/settings.test.ts`; the 11 tests passed in the 313.

- The function is `set_platform_setting(key, value, reason)` only; the two-argument version is gone (a test asserts exactly one overload and no `anon`/`public` execute).
- Unknown keys (including SQL-looking and whitespace/case variants) are refused with `unknown_setting`; a table trigger also refuses an insert of a key with no rule, even from the service role (a `SECURITY DEFINER` trigger; the earlier non-definer version caused the nine e2e failures and is covered by a service-role test).
- Wrong types, malformed and out-of-range values change nothing; locked keys cannot be changed; reasons shorter than 10 or longer than 500 characters, null or blank are refused.
- A valid change by a platform administrator at aal2 writes an audit row with actor, old value, new value, reason and outcome; audit rows are immutable (tested). Unauthenticated, customer, support, finance and aal1-admin callers are refused (42501).
- The `support_email` test now uses `max_cart_item_quantity`, as the handoff says.
- Not covered: failed attempts are rolled back and therefore not audited in the database (documented).

## 8. Accessibility assessment, including the signature gap

Verified from code and tests (`signature-pad.tsx`, `signature.ts`, `complete_delivery`, `accessibility-keyboard.spec.ts`):

- **Input methods:** pointer events (touch, stylus, mouse) draw on a canvas; **keyboard-only users cannot complete the signature** (the canvas has no tab stop and no key handling; a test pins this).
- **Validation:** client requires >= 150 dark pixels (a dot or a tap is not a signature); the server accepts only a PNG data URL between 300 bytes and 400 KB; the database re-checks size and PNG magic bytes, requires `capture_method = 'drawn'`, refuses typed acknowledgement, and stores the image with its SHA-256.
- **Empty canvas:** the form shows "Please sign in the box before confirming." (visible in the screenshot audit); nothing completes.
- **Announcements and focus:** the error uses `role="alert"`; the pad's state text ("Nothing signed yet" / "Signature captured") is `aria-live="polite"`. Whether focus moves to the error was not verified (no screen-reader or focus-after-error test exists).
- **Clear and redraw:** the "Clear signature" button resets the canvas.
- **Linkage:** the signature is bound by a one-time, expiring, hashed proof token to the current assignment and order; the rider never sees it.
- **Alternative:** none in the interface except the "Get help from support" link and the support exception path. A typed alternative exists in code but is **disabled** and was not enabled.
- **Not done:** no screen-reader, real-device or person-led review. An accessible-design proposal for the owner is in `docs/accessibility-signature-proposal.md`. No delivery-proof rule was changed.

The manual review checklist is in `docs/testing/manual-accessibility-checklist.md`; **it is a checklist, not evidence that a review happened.** Statuses: keyboard/focus/320 px reflow on the main screens: automated (passed); everything else: requires a person and a device (blocked here).
