## C. Settings security (K59, K63)

**Findings.** `set_platform_setting(key, value)` accepted any key from an administrator (it upserted unknown keys), took no reason, and audited only the new value.
**Changes** (migration `20261016000001`): one rule table `app_private.setting_rule(key)` (int ranges, boolean, enum, return-policy object, locked) is the single source; the three-argument function `set_platform_setting(key, value, reason)` replaces the two-argument one (dropped, so no reason-less path exists); unknown key → `unknown_setting`; wrong type/range → `invalid value`/`out of range`; reason 10–500 characters after control characters are turned into spaces; locked keys (`mock_payments_enabled`, `rider_terms_current_version`, `settlement_policy` ≠ `DISABLED`) refused; audit entry holds actor, setting, **old value, new value, reason, outcome**; a table trigger (`SECURITY DEFINER`) also refuses inserting any key without a rule, so even the service role cannot add one. The settings page and server action collect and validate the reason; the action logs only the setting name and SQL state. A failed change raises, so nothing is partly updated and no success audit row exists; failed attempts are therefore not audited in the database (documented).
**Tests** (`tests/db/settings.test.ts`, 11): unauthenticated, customer, support, finance, admin at aal1 all refused with 42501; unknown keys (incl. SQL-looking and case/whitespace variants); table-level refusal; service role may upsert known keys but not unknown; locked keys; 16 wrong-type/out-of-range cases leave values unchanged; missing/null/empty/blank/short/long reasons; valid change writes the exact audit record and the record is immutable; boolean/enum/return-policy; no two-argument overload and no `anon`/`public` execute; refused changes leave no audit row. Existing tests that called the old signature were updated to pass a reason, and the one test that relied on an unknown key (`support_email`) now uses `max_cart_item_quantity` — an intended consequence of the requirement, noted here rather than hidden. e2e: reason required in the UI, audited with old/new/reason.
**Defect found by the full run:** my first trigger was not `SECURITY DEFINER`, so e2e fixtures (service role) got `permission denied for function setting_rule` (9 failures). Fixed and covered by a DB test that exercises the service role.
