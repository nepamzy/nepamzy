# Data inventory, retention and minimisation (engineering view)

This is an **engineering inventory of what the application stores**, not a legal assessment. Whether the pilot satisfies Nigerian data-protection law (NDPA 2023, NDPC requirements) is for legal review; nothing here claims compliance. **Retention periods are not decided**: where the table says "unresolved", the application keeps the data until the owner/legal sets a rule. Where a period exists in configuration it is a placeholder.

Real campus coordinates are not stored anywhere (delivery points and geofences are synthetic); tests use synthetic points only.

## Minimisation review

- **Notifications** carry nothing the user cannot already see in their own authenticated view, and usually less. A test scans every generated title and body for money, codes, tokens, signatures and coordinates.
- **Public reviews** expose rating, comment and date. The author, the order and the shop staff's identities are not returned (`get_vendor_reviews`).
- **Location** is collected only during an active shift with an accepted delivery, validated, stored with a short placeholder retention and never read by other customers. A missing fix never changes an order.
- **Signatures** are mandatory proof for delivery completion; they are not shown back to anyone through the API and are stored as an image in the database for now (K26).
- **Logs** pass through a redaction filter that blanks values whose key looks like a password, token, secret, cookie, code or signature. Audit entries never contain secrets.
- Free-text fields (case statements, review comments, refund reasons) cannot be fully policed; users are told what not to include. Moderation hides but does not delete.

## Data-subject requests (plan, not implemented)

- **Access/export:** no export tool exists. A manual procedure would be: an administrator with a recorded purpose queries the tables above by user id. This needs a written procedure, an identity check, and a way to record the request.
- **Deletion:** not implemented. Money, audit and dispute records are append-only by design and likely need to be kept for a legal period (unknown). A deletion design would need to separate what can be erased (profile, notification history, carts, reviews' link to the author) from what must be retained (ledger, audit), and a decision on anonymisation instead of erasure.
- **Correction:** users can change their display name only.
- **Who answers requests, within what time, and where requests are logged:** awaiting owner and legal review.

## Safe interim behaviour (what the code does while decisions are open)

- Keep everything; delete only what an existing, tested purge covers (location history) when someone chooses to run it.
- Never auto-delete money, signatures, dispute evidence or audit history.
- A deletion or access request cannot be fulfilled through the application today. It would be a manual, recorded administrator task, and no procedure for that has been approved.

## Dependencies a future purge must respect

A purge must (1) skip anything attached to an open or recently closed dispute, refund or reconciliation flag, (2) run in bounded batches, (3) be idempotent, (4) record its own run in `job_runs`, (5) be reviewed by counsel before it is scheduled, and (6) be tested against the restore drill's content hash so that a restore never resurrects purged rows by surprise.
